# ADR 0009: Project bootstrap (Paperclip plugin + `bootstrap` task type)

## Status

Accepted and implemented (2026-10-23). Verified with the fake provider and mocked host steps; the end-to-end run with real providers is recorded in `docs/engineering/knowledge/metrics/runs/`.

## Context

Creating a project was manual: a Paperclip project, a hand-written `projects/<uuid>.json` manifest, a workspace folder, a git repository with `origin`, then hand-written tasks. We want the user to describe a project once in the Paperclip UI and get a planned, constrained, AI-ready project: stack decision, project contract, milestones and tasks with dependencies, a generated repository with agent guides and an initial commit, and the issues in Paperclip.

Facts about the pinned Paperclip (`v2026.916.1`, `.runtime/paperclip`), checked in its source and in the running container:
- A plugin system exists (`packages/plugins/sdk`, published as `@paperclipai/plugin-sdk@2026.916.1`, the same version as the host): UI slots (`page`, `sidebar`, `globalToolbarButton`, `detailTab`, `settingsPage`), a capability-gated worker, local-path or npm install, and `apiVersion` checks at install.
- The core "New project" dialog has no plugin slot (`openNewProject` in `ui/src/pages/Projects.tsx`), so the plugin adds its own entry points instead of patching the dialog.
- There is no milestone or phase object. Available: goals, parent and sub-issues, `blockedBy`, labels, issue documents.
- Plugin UI is same-origin trusted code. Plugin workers get a minimal environment (no `process.env` pass-through), so the bridge token is a plugin secret reference.
- Plugins install under `~/.paperclip/plugins`; in the container `HOME=/paperclip`, the bind mount `data/paperclip`, so installs survive rebuilds.

## Decision

1. **Plugin for the UI, orchestrator for the logic.** `plugins/project-bootstrap/` is a separate package (no Paperclip core edits). It adds a wizard `page` (`/new-project`), a `sidebar` entry, a `globalToolbarButton` and a project `detailTab` ("Bootstrap": progress, plan, approval, result). Its worker is a thin authenticated proxy to the bridge (`catalog`, `status`, `resolve`, `approve`, `reject`); it holds no logic. The page creates the project and the planning task with the board user's own session through Paperclip's REST API, so nothing in the plugin needs more than `http.outbound`, `secrets.read-ref` and the UI slots. A Paperclip upgrade can affect only the slots, the SDK calls and the REST calls; the SDK is pinned to the host's version.
2. **One catalog, served by the bridge.** `src/bootstrap-options.ts` defines every option (platform, maturity, architecture, stack, UI/UX, test depth, visual verification, review rounds, OpenSpec, analysis, CI, accessibility, data, hosting, task size, autostart, approval, repository) with a default and a simple/advanced flag. `GET /v1/bootstrap/catalog` serves it and `POST /v1/bootstrap/resolve` resolves a selection, so the wizard renders from data and never hard-codes a field. A maturity preset (throwaway, prototype, MVP, production) sets defaults; the precedence is the user's explicit value, then the preset, then the default, and a value the user touched is never overwritten. Platform rules derive values (for example no visual checks for a mobile project) and say so. End-to-end tests are never selected below production unless the user asks.
3. **A `bootstrap` task type** (ADR 0008 registry, `taskFlow: "bootstrap"`). The form travels in the Paperclip task description as a hidden `<!-- bootstrap-form ... -->` block; the bridge recognises the `type:bootstrap` label, validates the form, resolves the options, and starts the workflow without a project manifest (the project does not exist yet). Stages, all through `structuredStage` (validate, repair with diagnostics, deterministic fallback, covered by the chaos table): `stack` (model recommendation from its own knowledge, with alternatives, assumptions and risks, or the user's stack), `charter` (the project contract), `blueprint` (milestones, tasks, acceptance, dependencies, bounded by task-size limits). Fallbacks never invent a recommendation: the user's own stack or the one templated web stack, the user's own words, one task carrying the whole description.
4. **Approval gate** on by default. The run stops after planning (`bootstrapStateQuery` exposes the plan), the project's Bootstrap tab shows it, and approve or reject signals the workflow. Only after approval are the repository, manifest and issues created. Rejection creates nothing.
5. **Scaffold on the host worker** (`scaffoldProject`): writes the files, installs the current releases of the template's packages and commits the lockfile (so templates carry no stale versions), proves `npm test` and `npm run build` before anything is committed, commits, creates a private GitHub repository with `gh repo create --push` (the write-capable login stays on the worker, never in the bridge container or model runs), and writes `projects/generated/<paperclip-project-uuid>.json`, validated with `ProjectManifestSchema`. The bridge re-reads manifests when it sees an unknown project id, so no restart is needed. Before the repository exists a failure removes everything it created; after it exists the folder is kept and the message says what to clean up. A stack without a template still gets the contract, plan and docs, with a warning, and its tasks wait in the backlog because the orchestrator can only run code tasks once the manifest has quality commands (non-Node stacks stay deferred: B-021, B-022).
6. **Paperclip issues** (`materializeIssues`, host worker, the worker's board API token): milestones are parent issues labelled `milestone`; tasks are their children with `blockedBy` for dependencies; a task with no dependency inside its milestone waits for the last tasks of the previous milestone, so milestones run in order. Tasks go to the orchestrator agent; `autostart` decides what starts in `todo` (none, first milestone, all) and the rest stays in `backlog`. Read-only investigations get a `type:research` or `type:architecture` label.
7. **Project contract and agent guides.** The repository gets `docs/PROJECT_CONTRACT.md` (vision, goals, non-goals, boundaries, constraints, design rules, quality bar, definition of done, drift rules, and the configuration chosen with where each value came from), `CLAUDE.md` and identical `AGENTS.md` (Claude Code and Codex load these automatically in every task worktree), `docs/PLAN.md` and an ADR for the stack. Every generated task description ends with a pointer to the contract. Injecting the contract into the task prompt itself was rejected for now: the hard-constraint extraction in `handoffs.ts` treats every "must not" sentence as protected text with a token budget, so a long contract would starve the brief; a dedicated workflow channel needs `patched()` and a replay fixture and is a follow-up.
8. **Global configuration** lives in `bootstrap.global.json` (next to `uiux.global.json`): the provider routes of the three bootstrap stages and the defaults written into every generated manifest. The generated manifest is the project's own copy afterwards. Precedence is documented in `docs/engineering/knowledge/config-schema.md`.
9. **Adapter.** A completed bootstrap marks its Paperclip task done and posts the plan; a rejected plan cancels it; a failed one stays open with guidance about leftovers. This needs a Paperclip container restart because the adapter is loaded at startup.

## Consequences

- No Paperclip core change. The coupling is the plugin SDK `apiVersion`, Paperclip's issue, label, project and agent REST routes, and the adapter contract.
- Workflow impact: a new branch selected by `input.taskType === "bootstrap"`, three new proxied activities with one attempt each, one new query. No existing command sequence changed; the replay fixture is unchanged and passes.
- `RunResult` gains `bootstrap` and `RunInput` gains `bootstrap`; `StageName` gains `stack`, `charter`, `blueprint` (manifest routes and timeouts accept them).
- Deploy touches four places: build and restart the worker, rebuild the bridge container, recreate the Paperclip container (new read-only mount of the plugin folder, adapter reload), install the plugin (admin) and set its two settings.
- Risks: the plugin API is "alpha" upstream (mitigated by the pinned SDK and an `apiVersion` check at install); plan quality depends on the model (bounded sizes, repair, fallbacks, human gate); creating a GitHub repository is outward-facing (private by default, explicit option, approval gate); `npm install` at scaffold time needs network access.
- Not covered: adopting an existing Paperclip project, non-Node quality gates, web search for stack recommendations (the stage prompt asks the model to state its assumed versions; a search source can be added behind the same stage), amending the contract through the board, cost budgets for the bootstrap run, a settings screen beyond the plugin's JSON-schema form.

## Addendum (2026-10-23, live build)
Four things the first real build showed, now part of the design: the form is base64url because Paperclip rewrites escape sequences in task text; plans are strictly sequential because a task can have one blocker and parallel tasks on a small app conflict; the bridge supplies the projects folder; and every publication closes the open PRs of earlier runs of the same task (Paperclip's review path reruns tasks, each run has its own branch), so one task has one open PR. `npm run reconcile` reports results that finished while Paperclip was disconnected. See `knowledge/failure-modes.yaml` FM-040 to FM-044 and `knowledge/metrics/runs/2026-10-23-bootstrap-aurora-store.json`.

## Addendum (2026-10-24, SSRF guard bypass)
The plugin worker first called the bridge through `ctx.http.fetch`. Paperclip's host (`plugin-host-services.js`) resolves the hostname and refuses it when every resolved IP is private or reserved, with no opt-out, so `http://orchestrator:3101` always failed with "All resolved IPs for orchestrator are in private/reserved ranges". The worker now uses its own `fetch` for the bridge call, which deliberately bypasses that host guard. Accepted because the target is an internal service the operator configures in the plugin settings and the call is authenticated with the bridge token; the cost is that the guard no longer constrains this URL, so the setting must only ever be set by an instance admin. The alternative, giving the bridge a public address, was rejected as a larger exposure. The `http.outbound` capability stays declared.
