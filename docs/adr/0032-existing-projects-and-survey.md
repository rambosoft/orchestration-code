# ADR 0032: Existing projects (maintain, refactor, migrate, audit) and the survey stage

Status: Proposed (2026-11-02). B-107 first slice implemented (folder checks, mode option); the rest is design. Extends ADR 0009 (bootstrap), ADR 0008 (task types) and ADR 0017 (`onboard`).

## Context
- The bootstrap wizard only creates new projects. An existing repository can be registered with the `onboard` CLI (ADR 0017), but the wizard has no way to choose a folder, no notion of why the project is being adopted, and nothing that studies the code before tasks are planned.
- The first real case is `luxus-app` (Vue 2 + Nuxt 2, JavaScript, Node 14, about 86 pages, 264 components, 35 Vuex modules, 51 plugins) to be rebuilt as a client-side React app. It is a TV app (Tizen and webOS) whose docs still list Chrome 38-class devices as in progress, so the target must be tiered: a modern bundle plus a legacy bundle for Chrome 53 and up. Older devices keep the Vue 2 build or get a Preact build until usage data lets them be dropped.
- A migration done as free-form "port page X" tasks drifts in conventions, copies instead of restructuring, and has no proof of equal behaviour. ADR 0008 listed a behaviour-preserving refactor flow as not done.
- Operator decisions (2026-11-02): the new code lives in a **new sibling repository** with the old app mounted read-only as the reference; the first version supports **audit only, refactor/clean-up, upgrade/migrate and maintain**; the folder is chosen with a **path field plus a browser limited to allow-listed roots**; the TV target is **tiered**.

## Decision

1. **Entry mode.** The wizard's first step is `New` or `Existing`. `New` is the current flow, unchanged. `Existing` asks for a folder, then a `mode` option added to the catalog (`src/bootstrap-options.ts`): `maintain`, `refactor`, `migrate`, `audit`. A mode sets defaults like a maturity preset does (user value, then mode preset, then default).
2. **Folder selection.** A browser page cannot open a native picker, so the wizard has a path field plus a folder listing served by the bridge from the **host worker**. Only roots in an allow-list (`ORCHESTRATOR_BROWSE_ROOTS`, default `C:\workspace`) are listed; the browser never sends a raw path to be read. The worker validates the chosen folder: it exists, is under an allow-listed root, is a git repository, has a clean tree, and names its remote. Anything else is refused with the reason. Detection of stack and quality commands reuses `onboard`.
3. **Target location.** `refactor` and `migrate` write to a new sibling repository (same scaffold and `gh repo create` path as bootstrap, ADR 0009 decision 5). The source repository is recorded in the manifest as a read-only reference (`reference.root`); a task worktree gets it mounted outside the writable tree and the publish guard refuses any change to it. `maintain` works in the adopted repository itself. `audit` writes only a report document (a draft PR of kind `document`, as research does).
4. **`survey` stage.** A read-only stage (not the ADR 0005 `analysis` stage, which compares approaches inside one task) that studies the adopted repository before any task is planned.
   - Input: a deterministic, redacted, size-bounded context pack (extends `src/context-pack.ts`: file map, entry points, route and store inventory from stack-specific extractors, dependency ages, test inventory, duplication and dead-code tool output when available) plus fixed guidance per mode.
   - Provider: a route `providerRouting.survey`, Codex by default, any provider allowed.
   - Output, through `structuredStage` (validate, one repair pass with diagnostics, deterministic fallback in `src/fallbacks.ts`, a row in the chaos table): architecture map, module and route inventory, duplicated logic, hotspots, risks, test coverage, dependency and runtime age, constraints found in the repository's own docs (for `luxus-app`: the device compatibility rules), and a **sized refactor backlog** where each item names the old files, the target shape and the tests that prove it. Evidence references are required; an item without evidence is dropped.
   - The report is committed as `docs/survey/<project>.md` in the target (or as the audit document), and posted as the issue comment.
5. **From report to plan.** After the human approval gate (ADR 0009 decision 4) the survey report feeds the existing `blueprint` stage as its input, so milestones and tasks come from the sized backlog instead of a free-text description. `audit` ends at the report. Tasks are vertical slices (one page or store module with its tests), ordered by dependency.
6. **Refactor and migrate flow.** For these modes each slice runs: `characterize` (write tests or Playwright specs against the reference behaviour; `verifyReproduction` is reused to confirm they pass on the old code), then the existing plan, brief, implement, review and verify. The verify gate adds a **parity check** (the characterization tests pass on the new code) and the gates in decision 7. A `migration-map` file in the target (old file, new file, status, tests) is updated by every task and lets a later run resume; it is data, not workflow state.
7. **Quality rules, enforced by gates, not only by prompt.** The project contract (ADR 0011) gains a "refactor, do not copy" section: logic that is not view code moves to hooks or utilities, shared UI to one folder, no duplicated component, no dead code, boundaries between feature folders. Gates are optional activity-level checks (so no new workflow step and an unchanged replay fixture): duplication (`jscpd`), dead code (`knip`), import boundaries (`dependency-cruiser`), strict TypeScript, and for React the hooks and accessibility lint rules, Vitest with Testing Library, and a bundle-size budget. The review prompt asks specifically whether code was ported verbatim instead of restructured. Every gate is a node/npm command, which the current allow-list already permits.
8. **AI-ready output.** The scaffold and every task completion keep these current: `CLAUDE.md` and identical `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/ai/map.md` (module map and where things live), ADRs for decisions, and a short README per feature module. A task is not done if the map is missing a module it added (checked by a deterministic script gate).
9. **Reuse over invention.** A stack pack (ADR 0017) gains a `references` list: the installed skills, agents and libraries stage prompts must name and prefer (for the React pack: `react-patterns`, `react-testing`, `vite-patterns`, `e2e-testing`, and the matching reviewer agents; TanStack Query, a small state library, a router, a spatial-navigation library for TV focus). A new dependency outside the pack's allow-list needs a recorded reason, checked against `package.json` by a hygiene gate. Versions are verified at scaffold time, not taken from memory.
10. **Vue 2/Nuxt 2 to React pack (first migration pack).** An idiom map (Vuex to a small store, `asyncData`/`fetch` to query hooks, mixins to hooks, middleware to route guards, `@nuxtjs/i18n` to a React i18n library, client plugins to providers), a **device-tier matrix** in the contract (modern bundle; legacy bundle through the Vite legacy plugin for Chrome 53 and up; the project's existing Chrome 38 audit, bundle budget and banned-API list reused as the legacy gate; styling limited to what the legacy tier supports), and the player adapters ported unchanged behind a thin React wrapper.

## Consequences
- Workflow impact: new typed branches selected by `input.taskType` or mode (`survey`, `characterize`), the same way ADR 0008 and ADR 0009 added theirs; no existing command sequence changes, so no `patched()` and the replay fixture stays. If a later phase changes the sequence, it needs `patched()` and a regenerated fixture (`docs/engineering/EXTENDING.md`).
- New provider routes: `providerRouting.survey`, `providerRouting.characterize`. New stage names in the manifest schema, with timeouts.
- New bridge endpoints for folder browsing and validation; they must refuse anything outside the allow-listed roots and never echo file contents.
- The survey is only as good as its context pack and guidance; the schema, the repair pass, the evidence requirement and the approval gate bound the damage, as in the other structured stages.
- Admission needs a clean tree: `luxus-app` has uncommitted changes that must be committed or stashed first.
- Not covered: Flutter, Android and other stacks (they get their own packs), merging the old and new repositories, automatic deletion of the reference, usage analytics for dropping a device tier.

## Open points
- The exact survey report schema and the per-stack extractors (Vue 2/Nuxt 2 first) are designed in phase 2, with a real run on `luxus-app` as the first evidence.
- Whether `characterize` is its own typed flow or a prelude inside the implement stage is decided in phase 3 from timing data.
- The device tier cutoff stays a project option until real device-version data (the app already collects versions) says which tiers can be dropped.

## Addendum (2026-11-02): operator requirements for the migration
- **Pilot:** one simple page first, `pages/no-internet` of luxus-app (103 lines), into a local sibling folder `C:workspaceluxus-app-react` (no GitHub repository until the pilot is judged good). luxus-app must be clean first (it has uncommitted changes).
- **Rethink, do not transliterate.** The old code is messy, so the survey and the tasks reconsider structure instead of assuming it follows best practice: extract components where it makes sense, move logic to hooks and utilities, one clear place for each thing.
- **Findings are written down.** Survey and implement stages record findings and TODOs they could not finish in the target repo (`docs/migration/findings.md`, `docs/migration/todo.md`), with file references. Changes that would alter architecture or behaviour are NOT made silently: migrate with the least change, point it out, and document it for a decision.
- **Production ready, simplest, cleanest**, React and stack best practices, all screen sizes, and the tiered devices agreed earlier (modern + legacy Chrome 53+).
- **Sizing:** one root scale token (a single unit derived from `vh` with a `vh` fallback; sizes in `rem`/`em` from it) so one file retunes every screen size. Raw `vh` values are not repeated across components. Legacy tier needs Chrome 49+ for CSS variables, which the Chrome 53+ floor satisfies.
- **Speed and cost:** many tasks are expected. Survey (analysis) runs once per milestone or domain, not per page. Every task runs the cheap deterministic gates (types, lint, unit tests, parity spec, duplication and dead-code checks); the model review runs once per milestone, like the prototype lane (ADR 0029, 0031). Cheaper providers for survey and characterize are allowed through the routing.
