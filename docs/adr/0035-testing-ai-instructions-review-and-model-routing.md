# ADR 0035: Layered testing, canonical AI instructions, rule-aware review, per-area model routing

Status: Proposed (2026-11-02). Design only: no code yet. Builds on ADR 0032 (existing projects), ADR 0033 (skill catalog), ADR 0034 (engineering constitution) and ADR 0015/0029/0031 (lanes, one review per milestone for prototypes).

## Context
- A migration has hundreds of small tasks. Test and review cost per task decides whether it finishes. The operator asks for: few tests that still cover the happy and the unhappy cases, runnable per domain, targeted while implementing, wide only after a milestone; a few end-to-end journeys that each cover many cases; parallel runs wherever possible; faster reviews; short, consistent AI instruction files for every agent; reviews that check the rules and what is actually enforced; the strongest model only where the risk is highest; and an orchestration that gets faster as it learns.
- Found in the repository (2026-11-02): `src/test-strategy.ts` already tells the implementer to run only affected tests, as a prompt hint that nothing enforces. Provider routing is per stage (`provider`, `model`, `reasoningEffort`), not per area or task. Quality commands run one after another (B-059 parallel gates is `todo`). `CLAUDE.md` and `AGENTS.md` are generated with identical content. The reviewer checks the diff against the project contract, not against an enforced rule list.
- Decisions taken with the operator: tasks in **different areas with disjoint files may run in parallel**, tasks in one area run in sequence; **Opus is used for implementing critical areas only** (cache and storage, player, iframe bridge, carousel, search and sort, Xtream fetch), reviews and all other work use Codex or Sonnet; behaviour parity comes from **page behaviour specs plus recorded or mock API fixtures**, not from running the old app.

## Decision

1. **Four test layers.**
   - *Per task (seconds):* typecheck, lint of changed files, and the tests related to the changed files (`vitest related`) plus the unit tests of the touched domain, run in parallel and fail fast. Domain scripts `test:<domain>` (input, storage, catalog, bridge, ui and so on) are a pack convention, so a change runs only its area.
   - *Per milestone (minutes):* the full unit and integration suites, the bridge contract suite against the host simulator, bundle size and heap budgets, accessibility smoke.
   - *End-to-end after a milestone:* four to five wide journeys, each covering many cases with happy and unhappy paths: first launch to playback; failures (bad credentials, offline, http provider, server error mid-list, storage quota, rapid remote navigation, stale responses); search and sort on the large mock catalogue under a memory budget; live TV zapping with the EPG; host-bridge races (handshake order, lost message, wrong origin).
   - *Devices:* emulators (Android TV, Tizen, webOS) and real TVs after a milestone or after several pages, never per task; results are recorded as a report that a person signs off.
2. **Few tests, all cases.** Each page document lists its cases (the case matrix: states, actions, edge cases, inputs). A gate checks that every listed case id is referenced by a test, and that a test cites a case id. Logic is tested with table-driven and property tests, so a small number of tests covers many inputs. Characterization for a migrated page uses the behaviour spec and API fixtures (recorded responses or the mock Xtream server), not the old application.
3. **Enforced, cheap, parallel.** The affected-test hint becomes a gate: the verify step for a task runs only the affected set, independent checks run concurrently with fail-fast, and the milestone check task runs the wide set (extends ADR 0018). Command output is compacted before it reaches a model (`rtk`, `log-compact`).
4. **One canonical AI instruction file.** `AGENTS.md` is the single source: imperative, dense, machine-oriented, numbered rule ids (`R-001`), a size budget (about 150 lines), links to the standards and the map. `CLAUDE.md` and any other agent file only point to it. A gate checks the size and the pointers, so Codex, Claude and any later agent receive the same rules.
5. **Enforcement manifest.** `docs/ai/enforcement.json` maps every rule id to the gate that enforces it, or marks it prose-only. It is generated from the pack and checked by a gate.
6. **Rule-aware, risk-based review.** The reviewer gets the digest of the prose-only rules, the enforcement manifest and the gate results, reviews the diff against them, and every finding must cite a rule id; findings with no rule id are dropped, which removes generic and unrelated review comments. Low-risk tasks with green gates are reviewed with the milestone; tasks touching a critical area, adding a dependency, or flagged "changes behaviour" get a focused review of the diff with the rule digest only. Risk is computed from the area, size, paths and flags (a deterministic function, not a model call). This replaces the per-task escalation of ADR 0015 for the migration lane.
7. **Per-area model routing.** The survey tags each backlog item with `area` and `critical` (from the performance registry of ADR 0034). The bridge turns the tag into a route override on the run input (data, no workflow change): critical implement tasks use the strongest model (Opus) with high effort; other implement tasks use Sonnet; analysis, mapping, survey context and reviews use Codex or Sonnet. The manifest holds the table (`areaRouting`), a per-run cost cap, and fallbacks. Current model ids and prices are confirmed when the table is written.
8. **Parallel tasks by area.** A backlog item carries its area and the files it owns. The scheduler runs items of different areas with disjoint ownership in parallel (`plan_mode=parallel` with integration branches), and items of one area in sequence. An overlap found at run time falls back to sequence. This avoids the same-line conflicts of FM-045.
9. **Getting faster with time.** The first components set the patterns and are slower on purpose; every decision is written into the project's patterns and standards. A page recipe and a component recipe (deterministic scaffolding) shrink the model's part to the real logic; a reuse index lists existing shared components before planning; metrics track time, cost and repair rounds per task so improvement is visible; recurring review findings become lessons (ADR 0033, decision 7).
10. **Deterministic extraction before model reading.** The survey parses `.vue` files with `@vue/compiler-sfc` (props, store usage, used components, sizes) and uses codemods (`ts-morph`, `jscodeshift`) for mechanical rewrites such as imports and renames. Models interpret; tools count.

## Consequences
- Per-task cost falls (targeted tests, compact output, no routine model review), and quality rises where it matters (strongest model and specialist review on critical areas, gates for everything a tool can check).
- A rule that is neither a gate nor listed as prose-only is a defect in the pack.
- The migration lane needs its own definition (strict gates per task, review by risk, wide checks per milestone); it is not the prototype lane.
- Workflow impact: route overrides, risk routing and the case-matrix and size gates are data or activity-level checks. Parallel scheduling touches plan ordering, not the stage sequence. No `patched()` is expected; any change that alters the command sequence needs it and a regenerated replay fixture.
- Not covered: test generation by models beyond the case matrix, cross-browser matrices beyond the pinned engines, performance testing on real TVs per task.

## Open points
- The risk function (weights, thresholds) is set from the pilot's measurements.
- The exact area list and ownership globs come from the `luxus-app` survey.
- Whether the milestone e2e journeys run against emulators or the host simulator by default (ADR 0036 decides the simulator).

## Addendum (2026-11-03): rule-aware and specialist review built (B-134, B-129)
- **Rule-aware review (activity side, no workflow change).** When the worktree has `AGENTS.md` and `docs/ai/enforcement.json` (the react-ts-vite pack), the review prompt gets the rules a gate already checks, the prose-only rules spelled out, and the duty to give every finding a `rule` (R-nnn, a case id C-nnn, or BUG with a concrete scenario). `requireRuleCitations` (`src/review.ts`) moves any other finding to the notes with its evidence, recomputes the verdict, and records `movedForNoRule`. A repository without a rule set gets the ordinary review. Code: `src/review-rules.ts`.
- **Specialist review (B-129).** The manifest `review.specialists` lists critical areas by path glob with a focus text. The workflow matches the files `assessChanges` reports (`src/review-policy.ts`): a match adds a focused review even to a prototype task (which otherwise reviews once per milestone) and puts the focus in the prompt of any review the lane already has. Data-gated on the run input: a run without `specialists` takes exactly the path it always did, so no `patched()` and an unchanged replay fixture (the replay test passes). `luxus-app-react` lists storage, input, xtream, carousel and player.
- **Not built:** the gate results are not copied into the review prompt; the deterministic checks still run beside the review and fail the task on their own. The "low-risk tasks reviewed with the milestone" half already existed as the prototype tier (ADR 0029).

## Addendum (2026-11-03): deterministic Vue extraction is built (B-138)
- `src/vue-extract.ts` reads a Vue 2 / Nuxt 2 single-file component into facts: name, props, registered components, mixins, lifecycle and Nuxt hooks (`asyncData`, `fetch`, `middleware`, `layout`), watcher, computed and method counts, the Vuex use (mapped state, getters, actions and mutations with their namespace, `dispatch`, `commit` and state reads, in the component or in `asyncData`), the event bus (`$nuxt.$emit/$on`), `$refs`, direct `window` or `document` access, the custom tags and the directive counts of the template. The script is parsed with the TypeScript compiler API (a real AST); the template is scanned as text.
- `buildSurveyInventory` adds a bounded "Vue components" section (largest first) and a "Vuex use by component count" section to the inventory the survey model reads. Run on the real legacy `luxus-app` (782 files) it takes about 1.4 seconds and reports for example the 6073-line `SmartVideoPlayer.vue` with its props, registrations, hooks, mixin, store calls, bus events, 10 `$refs` and 21 window/document accesses, and that `settings-dev` is used by 33 components.
- **Dependency decision.** No `@vue/compiler-sfc`, `ts-morph` or `jscodeshift` was added: the TypeScript compiler API gives a real AST for the script block, the template facts need only tag and directive scanning, and nothing consumes a codemod yet. `typescript` 5.9.3 moved from devDependencies to dependencies, because production code now imports it (the worker host has it either way; the bridge image does not run the inventory).
- Limits: `<script setup>` (Vue 3) is not read; a component built by a factory shows only what its file says; template expressions are not parsed. Codemod helpers wait for the first migration task that needs one.
