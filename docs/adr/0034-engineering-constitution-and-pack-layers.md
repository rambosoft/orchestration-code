# ADR 0034: Engineering constitution for React + TypeScript + Vite projects, and the pack layers

Status: Proposed (2026-11-02). Design only: no code yet. Builds on ADR 0033 (skill catalog), ADR 0032 (existing projects, migration packs) and ADR 0017 (stack packs). The rule text is drafted in `docs/standards/react-ts-vite.md`.

## Context
- The operator wants every React + TypeScript + Vite project (not a monorepo) to start from the same enforceable rules: short docs on public and heavy methods, one job per method (preferred, not strict), latest libraries that are easy to update, extraction of anything reusable into configurable components, rare custom styling, backward compatibility with old devices, a living page-behaviour document and an AI map, clean code, dead and duplicated code removed during refactoring, deferred work tracked with a reason, and strong memory and CPU discipline.
- The first consumer, `luxus-app`, adds platform demands: low-spec TVs, a hand-built carousel to protect, one central input system for remote, keyboard, mouse and touch, a multi-level local store, 1,000,000 catalogue items, Xtream servers, every screen size from a phone to a 100-inch TV.
- A review of the operator's rules (pasted 2026-11-02, from another assistant's analysis; its linked source could not be fetched) proposed a "constitution" of 12 areas, 12 skills, 10 specialist roles and 4 enforcement layers. The structure is sound; two points need care here: (a) specialist review on every task conflicts with the cost decision of ADR 0032 (cheap deterministic gates per task, one model review per milestone), and (b) a million-item guarantee may be impossible on the client alone.
- Checked in `luxus-app` (2026-11-02): 76 files handle key events directly; the content cache manager already has 23 files (scheduler, query, recovery, index payloads, metrics); 31 files use `indexedDB` or `localStorage` directly; the Xtream calls (`get_vod_streams`, `get_live_streams`, categories) fetch whole lists.

## Decision

1. **Three pack layers, so the rules are reusable.**
   - *Generic pack `react-ts-vite`* (any project): clean code, documentation, component design, dependency policy, styling tokens, tech-debt tracking, living documentation, lifecycle and cleanup, safe refactoring, testing, accessibility basics, unbounded-resource and performance-regression rules.
   - *Project pack `media-tv-app`* (media apps for low-spec devices): device and runtime compatibility matrix, performance budgets and memory tests, component performance registry, the unified input and spatial navigation system, the multi-level storage contract, large-catalogue rules, the responsive scale from 320 px to 4K and 100-inch TVs.
   - *Provider skill `xtream-provider-integration`*: endpoints, capability detection, normalisation, retry and security rules. Other providers get their own skill later.
   A project selects packs in its manifest; the catalog (ADR 0033) holds the skill digests, the pack holds detection, gates and rules. `luxus-app-react` selects all three; a plain web app selects only the generic pack.
2. **The constitution is one authoritative file per project**, `ENGINEERING_STANDARDS.md`, generated into the target repository from the selected packs, with `CLAUDE.md` and `AGENTS.md` pointing to it and short `.claude/rules/` files per area. Both Claude and Codex read it in every task worktree. The draft text is `docs/standards/react-ts-vite.md`.
3. **Four enforcement layers, with the weight on the third.** (1) The constitution; (2) agent instructions, rules and skills; (3) automated gates: strict TypeScript, ESLint (hooks, accessibility, a rule forbidding key listeners outside the input layer), `knip`, `jscpd`, `dependency-cruiser`, Vitest, Playwright, bundle and heap budgets, the page-spec and tech-debt checks; (4) review and acceptance: PR template, specialist review where required, performance evidence. A rule a tool can check is a gate; the rest is prose and is listed as such (ADR 0033, decision 4).
4. **Priorities written as acceptance criteria.** Performance, backward compatibility and maintainability are requirements of an implementation, not follow-up work. A change that works on a powerful desktop but causes memory pressure, slow navigation or broken remote control on the lowest supported device fails review.
5. **Critical subsystems get an owner, a contract and specialist review.** The cache and storage manager, input manager, carousel and other registered performance-critical components, playback services and the Xtream adapter are registered in a component performance registry with their constraints and test scenarios. A task that touches one is reviewed by the matching specialist (storage, input, performance, compatibility) **per task**. Other tasks keep the cheap path: deterministic gates per task and one model review per milestone. Specialist roles reuse existing reviewer agents and prompts; they are not ten new agents.
6. **Protect optimised components.** An existing performance-critical component (the carousel first) is not replaced by a generic library to shorten code. A task must first record how it mounts, prefetches, releases images, preserves focus, cleans up and behaves under rapid navigation and remount; the replacement or change must be measured on a low-spec profile and keep behaviour (`characterize` stage of ADR 0032). Better optimisations are applied or listed in the audit.
7. **Deferred work is tracked, never silent.** Code that stays temporary or deprecated carries `@deprecated` (with the replacement) or a `TODO(debt:ID)` tag, and a ledger entry with ID, reason, risk, next action, owner, tracking issue and review date (`docs/technical-debt/`). A gate fails on a tag without an entry, an entry without a tracking reference, or an expired review date.
8. **Living documentation in three layers.** `docs/pages/<page>.md` (purpose, what is visible and when, actions per kind of user, supported inputs, data dependencies, performance notes, known limits, kept short and human-readable), `docs/architecture/` (data flow, caching, input, decisions, component contracts) and `docs/ai/INDEX.md` (a map that links into the real documents and is generated, not a second copy). A change that affects page behaviour, actions or a contract updates the document in the same pull request (a gate checks coverage and links). A scheduled GitHub Action reports drift as an issue or a proposed pull request for human review; it never rewrites behaviour descriptions by itself.
9. **Dependencies.** Latest stable compatible releases at project start; lockfile committed; Node and package manager pinned; no abandoned library; every significant dependency has a recorded reason (and the ADR 0032 allow-list check); Renovate with grouped minor and patch updates, major updates reviewed on their own against the compatibility matrix, auto-merge only for chosen low-risk updates.
10. **Compatibility is a matrix, not an assumption.** Before implementation the project records minimum browser engines per device family, supported JS and CSS features, storage limits, codecs, key maps and network behaviour. Vite's default targets and its legacy plugin do not make old TVs work by themselves (syntax is transformed, missing APIs are not polyfilled), so each tier is proven by a build check and a smoke test on that engine. Storage schemas carry versions and migrations; saved user data is never destroyed by an update.
11. **Storage and cache.** Four levels: L1 hot memory (what is visible), L2 warm memory (nearby, bounded, evicted by policy), L3 IndexedDB (catalogue, indexes, preferences), L4 the remote source. Limits are configuration backed by measurements. Required: bounded caches, eviction, TTL per data class, indexed queries, schema migrations, deduplicated requests and controlled writes, cancellation, recovery from storage errors and quota errors, metrics and a diagnostics view, targeted invalidation, defined offline and stale behaviour, isolation by provider, account and profile, correct handling of incomplete imports, a failed refresh never destroying usable data. `localStorage` is not used for catalogue or frequently written data. The current manager is audited and kept behind a storage interface; it is not rewritten blind.
12. **Large catalogues.** The requirement is browsing at least 1,000,000 items without holding them in memory or the DOM: retrieve only what is needed, cursor or category paging where the provider allows, virtualised lists with bounded overscan, normalised metadata and indexes in IndexedDB, indexed local or remote search, prefetch by navigation pattern, cancellation of stale requests, de-duplication of overlapping pages, back-pressure under rapid remote input. **Limit stated up front:** Xtream's common Player API returns whole lists per call and is not a universal contract; if a provider only returns a huge unpaginated response, client-side virtualisation cannot remove the download, parse and memory cost. The `xtream-provider-integration` layer therefore detects provider capabilities, imports large responses in a worker in chunks and persists processed batches, and a **discovery task** decides whether the million-item guarantee needs an indexing proxy (the project's own `luxus-service` is the candidate) before the guarantee is promised.
13. **Input.** One input manager normalises remote, keyboard, mouse and touch into intents (move, select, back, scroll, long press, repeat), with a spatial navigation engine (focus registry, zones, restoration, modal containment, focus persistence across pages). Pages and components register focusable regions and declare behaviour; they do not own global key handling. Text fields and native controls keep their keys. Norigin Spatial Navigation is a candidate to evaluate against the target TVs and the carousel, not a decision. A lint rule forbids key listeners outside the input layer, which makes the rule a gate.
14. **Responsive and styling.** A design system of tokens (colour, type scale, spacing, radius, shadow, sizes, breakpoints, focus, motion) and documented variants; custom CSS is the exception; layouts differ per size class rather than scaling one layout; the single root scale unit agreed in ADR 0032; no hover-only function; visible focus; reduced motion; touch targets sized per WCAG 2.2; text scaling and zoom respected. Tested at representative widths from 320 px to 4K and on real TVs.
15. **Verification.** Startup, memory growth over repeated navigation (heap test through Playwright and the browser debugging protocol), long tasks, catalogue scale, carousel mounted-element bounds, storage failure and migration, network cancellation and retry, all inputs, responsive sizes, older engines, listener and timer cleanup, playback resource release. No performance change is accepted without what was measured, what changed and the result.

## Consequences
- Rules become versioned, reusable pack content that reaches Claude and Codex alike, enforced by gates where a tool can check them, and visible in reviews.
- The cost model stays: cheap deterministic gates on every task, one model review per milestone, specialist review only on critical subsystems.
- The million-item claim is conditional on provider capabilities and a discovery result; we do not promise it before that.
- Library names in this ADR (Norigin Spatial Navigation, TanStack Query and Virtual, Renovate, React Compiler) and the Vite, Playwright and WCAG statements come from a secondary source and must be verified against current documentation and the target devices at scaffold time.
- Not covered: a monorepo variant (Turborepo), building the first React project (the pilot of ADR 0032 does that), the Xtream proxy itself.

## Open points
- Whether `luxus-service` can index and page the provider catalogue (discovery task, B-128).
- The performance budgets (bundle, heap growth, long tasks) are set from measurements on the first low-spec device profile.
- The exact critical-subsystem list is finalised by the `luxus-app` survey.
