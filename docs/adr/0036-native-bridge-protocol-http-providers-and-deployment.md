# ADR 0036: Native bridge protocol, http providers, security and deployment of the shells

Status: Proposed (2026-11-02). Design only: no code yet. Builds on ADR 0032 to 0035. The shells are separate repositories (`webos-luxus`, `tizen/Tizen-Luxus-App`, `viseo-android`) and the deployment repo is `viseo-deployment`; this ADR defines the contract and the work, the orchestrator drives it per project.

## Context
- Read in the repositories (2026-11-02): the web app runs inside an iframe in the webOS and Tizen shells (`postMessage`) and inside a WebView in the Android shell (three `addJavascriptInterface` objects: `Android`, `AndroidClose`, `AndroidExoPlayer`). The web app has per-platform adapters, each in a V1 and a V2 copy (`NativeAdapterV2.js` alone is 1,587 lines).
- webOS has a documented protocol (`source`, `type`, `sessionId`, `loadTxId`); Tizen has a V2 rewrite with crash detection and focus recovery. Origins: `native-message-origin.js` falls back to `*` in both directions without a configured origin; the webOS host accepts messages with an empty origin; Tizen reads the origin from the event; Android exposes native objects to whatever page the WebView holds, over `http://`, and the Tizen `config.xml` has `<access origin="*">`.
- Reliability complaint: the exchange is not set up at a dependable moment (the host posts its environment on iframe load, the app can ask for it, but there is no handshake with retries and acknowledgements), and the protocol is shaped around the player.
- Xtream servers are mostly http. An https page cannot call or play http resources (mixed content), so the web app is deployed over http: the production nginx config redirects port 443 to `http://` (`return 301 http://$host$request_uri`). The deployment repo's own notes say bootstrap scripts contain embedded credential values or placeholders. A Tizen signing certificate (`author.p12`) sits in the workspace.
- Decisions taken with the operator: http providers are reached **through the native shell on the TVs and Android, with the site on https** (the current dual http/https deployment stays as a documented, temporary exception); device validation runs **after a milestone or several pages**, not per task; the webOS, Tizen and Android emulators are installed on the operator's machine (their paths are confirmed before the harness is written).

## Decision

1. **One versioned bridge protocol** for all shells and the web app. Envelope: `{ v, id, correlationId, channel, type, payload, ts }`; channels `system`, `player`, `network`, `storage`, `device`, `input`; request/response with a timeout and an error model (`code`, `message`, `retryable`); events are one-way. The spec lives in the web-app repository (`docs/architecture/native-bridge.md`) with a JSON schema and TypeScript types, and the shells vendor the schema. Unknown channels and versions are rejected with an error, never ignored.
2. **Handshake before use.** `hello` (app) → `host-env` (shell, with capabilities per channel and protocol version) → `ready`. The app retries `hello` with backoff until acknowledged, queues requests until ready, and treats a lost shell as an explicit state (offline overlay, retry) instead of failing silently. Every message after the handshake carries the session id so stale replies from an earlier page load are dropped (the webOS `sessionId`/`loadTxId` idea, generalised).
3. **One client in the web app.** A single `BridgeClient` with transports behind it (`postMessage` to the parent for webOS and Tizen; the Android web message port), request/response correlation, timeouts and typed channel APIs. The per-platform player adapters become thin users of the `player` channel; the V1/V2 duplicates are removed during the migration.
4. **Origin and trust.** The allowed origin comes from configuration per environment (local development may allow `*` in a debug build only). Both directions check origin **and** `event.source`; an empty origin is rejected; the shell builds its target origin from its configured app URL; the Tizen `<access>` entry lists the app origin and the provider hosts allowed by the `network` channel instead of `*`. The staging URL baked into the shells becomes build-time configuration; release builds have debugging off.
5. **Android hardening.** Navigation in the WebView is restricted to the allow-listed origins; the three JavaScript interfaces are replaced by an origin-restricted web message listener (androidx WebKit `addWebMessageListener`) if the oldest target Android TV versions support it, otherwise the interfaces stay but are removed from any non-allow-listed page and reduced to the bridge entry point. Mixed-content and cleartext settings are explicit and documented per build type.
6. **Native-mediated network channel.** For http (and https) Xtream servers the app asks the shell: `network.request` for API calls and `network.stream` for large lists (the shell streams and may parse natively), and `player.load` for http streams played by the native players, which allow cleartext through their own configuration (Tizen AVPlay, webOS media, ExoPlayer). Limits, because this is a request proxy: only `http` and `https`; only hosts the user has configured as a provider (registered once through the bridge, stored by the shell); response size and time limits; no forwarding of the app's cookies; credentials in URLs are redacted from every log. Plain browsers cannot use http providers; they show a clear message, or use the backend proxy if that option is ever adopted.
7. **Deployment of the site.** Move the site to https: nginx serves the app on 443 and stops redirecting to `http://`; HSTS only after the TVs are verified; a Content Security Policy without `upgrade-insecure-requests` (it would break http providers on shells that still need them); the dual http/https deployment remains only as a time-boxed exception with a ledger entry (ADR 0034, decision 7). Embedded credentials in the deployment scripts move to secrets. Whether every TV model accepts the https site (certificate chain, clock, firmware) is verified on the devices before the redirect is removed.
8. **Host simulator and device validation.** A host-simulator page embeds the web app in an iframe and loads the real webOS and Tizen host scripts; Playwright drives it with remote-control key events and the mock Xtream server (`mock-xtream-server`, including its large dataset mode). It runs per milestone in the orchestrator, together with pinned older Chromium engines for the legacy tier. Emulators (Android TV AVD, Tizen TV emulator, webOS) are driven by scripts after a milestone or several pages; real TVs before a release by a checklist. Device results are a recorded report, signed off by a person.
9. **Contract tests.** One contract suite (handshake, ordering, timeouts, wrong origin, stale session, unknown channel, message size) runs against the simulated hosts and against each shell's host script, so a shell cannot drift from the protocol.
10. **Secrets and hygiene.** The Tizen signing certificate and any keystore live outside the repositories and the shared workspace folder, referenced by build configuration. Duplicate old copies (`C:\workspace\Tizen-Luxus-App`, 2022) are archived or removed after confirming the current one is `tizen/Tizen-Luxus-App`.

## Consequences
- One protocol replaces three ad-hoc ones, so adding a capability (storage sync, device info, deep links) is a new channel, not a new adapter.
- The native shells become part of the product's security boundary and need their own tests and releases; changing the shells is outside the `luxus-app` migration but is on its critical path for http providers and for https.
- The https move can break devices with old certificate stores or wrong clocks; hence verification on devices first and the temporary exception.
- Not covered: a backend proxy for provider traffic (an option for plain browsers), end-to-end encryption of bridge messages, signing of the configuration.

## Open points
- Whether the oldest Android TV targets support the web message listener.
- Which TV models and firmware versions accept the https site (device test).
- Where the emulators and the webOS SDK are installed (to confirm before writing the harness).
- Which host script is the source of truth for Tizen (`tizen/Tizen-Luxus-App`) and webOS (`webos-luxus`), and their release process.

## Addendum (2026-11-02): answers
- Android `minSdk` is 23 (`viseo-android/app/build.gradle.kts`). The origin-restricted web message listener depends on the installed WebView, so the shell feature-detects it at run time and keeps the restricted interface as the fallback.
- webOS device validation is skipped in the pilot; the `ares` CLI is installed for a real TV later and no webOS simulator was found. Tizen Studio (emulator tools) and the Android emulator exist.
- https on devices is verified in Phase 4, before the redirect is removed. Secrets in `viseo-deployment` and the signing certificate are handled by the operator; agents only list locations. The 2022 Tizen copy is archived after its git status is checked.
