# ADR 0039: A task-size gate keeps implementation passes small and stops paying for oversized ones

Status: Accepted (2026-11-04). Extends ADR 0015 (lanes), ADR 0029 (prototype lane and test scope) and ADR 0030 (tiers). Number 0037 is unused.

## Context
- Luxus task R3 timed out twice at 45 minutes in `implement`. It named 14 files over 3 areas, more than one pass can finish.
- The Temporal retry of `implement` reused the half-written worktree of the previous attempt, so attempt 2 started from edits nobody had verified.
- A timeout was classified `transient`, so reconcile resumed the run automatically and paid for the same oversized task again.
- A Codex run that never edits anything burned the whole 45-minute silence watchdog before failing.

## Decision
Keep a task small enough for one implementation pass, and when it is not, fail early, never retry blindly and hand the split to a person.
1. **Estimator and limits** (`src/task-size.ts`, B-175). `estimateSize` counts files and areas (`areaOf`; root-level files share the area "."), from a measured diff or from the task text (`filesNamedIn`, which ignores framework names such as Node.js). `DEFAULT_SIZE_LIMITS` per tier (`production`: small up to 2 files, large from 10 files, at most 2 areas; `mvp` 2/12/3; `prototype` and `throwaway` 3/40/6). `sizeLimitsFor(manifest)` lays the manifest's `sizing` numbers over the tier defaults.
2. **Manifest options** (B-176, B-177). Optional `sizing`, `testScope` (`affected` applies the milestone filter of ADR 0029 on every tier, `full` gates every task on all commands) and `lanes` (stage list per lane; the schema requires implement and verify in each list, and `sizing.smallMaxFiles` below `sizing.largeMinFiles` when both are set). No shipped manifest changed. What each field gates:
   - `sizing` is the explicit opt-in for what changes how a run executes: only with a `sizing` block does admission fill the workflow input `sizing`, which turns on the Codex progress guard (item 6) and the lower escalation file limit (item 8). A `tier` alone does not.
   - The size estimate `size` and its `sizeWarning` are information only, set for code tasks (implementation and refactor profiles; not the bug, research or architecture flows) of a project with a `tier` or a `sizing` block.
   - Size-failure handling (items 4, 5 and 8: no blind retry, class `size`, never auto-resumed, a `needs split:` result) applies to every project, with or without these fields. See "Operator-visible change".
3. **Generation gate** (B-178). `planFromBacklog` with `limits` leaves large items out of the tasks and lists them in `needsSplit` with a `proposeSplit` proposal (parts grouped by area, each under the large cutoff); small items get `Lane: light`; `mergeSmall` merges consecutive small same-area items (never critical or dependent ones). The `plan-from-survey` CLI passes the limits from the project manifest, takes `--merge-small` and prints a "Needs a split" section (B-184).
4. **Failure class `size`** (B-179). `classifyFailure` returns `size` (escalate) for the provider guard's own form `<codex|claude|gemini> no progress:` or `SizeSuspected`, or a timeout / stall with the `implement:` prefix, before the transient patterns. "no progress" in prose or test output is not size. Other stages stay transient. A `size` failure is not resumable, so reconcile never auto-resumes it.
5. **Clean retry** (B-180). Only the main implement call carries `StageInput.cleanRetry` (the workflow sets it; a repair round never does, because its worktree holds the implementation it repairs). HEAD is the base (the worktree is committed only at publish), so attempt 1 records the pre-implement state under the run's artifacts folder: `git diff HEAD --binary` as a patch and the untracked, not ignored paths. A later activity attempt unstages, resets tracked files to HEAD, removes only untracked paths the snapshot did not have, and re-applies the patch, so OpenSpec output and other earlier stage output survive (warning `clean-retry: discarded the previous attempt's edits`). Every git step and removal is checked (`WorktreeResetError`). A missing snapshot resets nothing and warns `clean-retry skipped: no pre-implement snapshot`. Implement errors carry an `implement:` prefix.
6. **Codex progress guard** (B-181). A pure `progressVerdict` and a 30-second worktree sampler in `CliProvider.run` kill the process tree and fail with `codex no progress: <reason>` when a Codex implement run makes no first edit (`firstEditMinutes`) or goes idle (`idleMinutes`). The sample is `git status --porcelain` plus a hash of `git diff` (read capped at 5 MB, `git diff --stat` above it), so a re-edit of an already-modified file counts; a completed Codex `file_change` item counts as a file edit; a Codex command or turn event counts as progress. Only the main implement call carries `progress`, never a repair round.
7. **Admission signals** (B-182). A `Stages:` line is a directive only when every comma entry is a stage name; any other `Stages:` line (`Stages: forest, desert, snow`, an empty one) stays in the prompt as prose. The directive and the manifest `lanes` lists resolve to run input `stageList` / `stageListReason`; HTTP 400 only for conflicting directive lines, a code task without implement or verify, or `brief` without `plan` ("a brief needs a plan"). Admission also sets `sizing`, `size` and `sizeWarning` as gated in item 2 (`src/stage-admission.ts`).
8. **Workflow wiring** (B-183). The workflow reads the optional input: `stageList` replaces the lane's stages in canonical order (plan, brief, implement, review, verify, duplicates dropped) with a `stage list set` warning; on the main implement call it sets `cleanRetry` and, with `sizing`, the `progress` limits; with `sizing` the escalation review fires from `largeMinFiles` changed files (it passes `maxFiles: largeMinFiles - 1`, because `escalationReasons` fires above `maxFiles`); every result carries the admission estimate as `metadata.sizeEstimate`; an implement or repair-round failure of kind `size` becomes a `needs split:` result with `metadata.size` for every project.
9. **Report** (B-184). `src/size-report.ts`: `sizeReport` (bands, advice at 2 or more or 25% size-suspected), the "Needs a split" section (posted by reconcile, see Corrections), and the `size-report` CLI that compares the estimate with the outcome per run. `e2e --record` writes `sizeEstimate` for every outcome (read before the older `estimate` field) and never retries a size-suspected failure.

## Operator-visible change
Size-failure handling applies to every project, not only to projects with a `sizing` block. For an existing project this means: an implement timeout raised by the provider or a Codex stall (`implement: codex stalled: ...` without a connection-error message) is no longer retried by Temporal, is no longer auto-resumed by reconcile, and ends as a `needs split:` result for a person. Before, such a failure was retried and resumed as transient. The operator can veto this and gate it behind `sizing`.

## Reuse
Lanes, tiers and the milestone test filter are the existing ones (ADR 0015, 0029, 0030); the gate adds numbers per tier and a failure class, not a new lane or workflow step. `Lane: light` and the lane stage lists are the existing mechanism.

## Corrections found while planning
- The progress guard is Codex-only: only the Codex CLI emits item events and runs in a worktree we can sample; other providers keep the silence watchdog.
- The plan stage produces no file list, so the admission warning comes from the file names in the task text.
- Needs-split is a reconcile comment only: no status change and no worker write (FM-054 and the manual-first policy). In practice the Paperclip adapter (`paperclip-adapter/index.js`, the terminal-failure report) reports the failed run first: it posts its own failure comment, without the needs-split section and with a timeout branch that advises raising the stage timeout, and PATCHes the issue to `in_review`. Reconcile then sees the result as `already_reported`, so the "Needs a split" section reaches the issue only when the adapter report is missing. The adapter is deliberately not changed here (a change needs a Paperclip restart, B-032); tracked as B-187.
- While a Codex command is in flight (items started minus completed above zero) the idle verdict is suppressed; the 45-minute silence watchdog backs up a hung command. `no_first_edit` still applies at `firstEditMinutes` and only after a successful worktree sample, so a failing git never kills a run.
- The event counter is independent of the 1 MB stdout cap, so a chatty healthy run is not frozen into a false idle.

## Versioning impact
Task 9 (B-183) adds no workflow command: `stageList`, `sizing` and the size fields are optional run input read by existing steps, and the failure result carries extra data on the existing result. No `patched()` is needed. Evidence: `test/replay.test.ts` passes unchanged against the recorded history and `git status --short test/fixtures` is clean after the full suite. In-flight runs have no `stageList` or `sizing` and behave as before. Task 6's `implement:` prefix and clean retry live in activities, which are not replayed. The final-review fix wave (2026-11-04) is data as well: `cleanRetry` and `progress` on the existing main implement activity call, `metadata.sizeEstimate` on the result, a needs-split result without the `sizing` condition, and `largeMinFiles - 1` as the escalation limit; no new await, command or timer, and `test/replay.test.ts` passed before and after with `test/fixtures` unchanged. An in-flight run that reaches a size failure after the deploy now ends as `needs split:` instead of a plain failure (same commands, different result data).

## Known limits
- There is no warning after implement that compares the real changed-file count with the admission estimate; only the admission warning (task text) and the escalation review (sizing projects) look at file counts.
- The adapter's failure comment carries no needs-split section and advises raising the stage timeout for a size failure (B-187).
- The clean retry never touches an untracked path that existed before implement, so a failed attempt's edits to such a path survive the restore. The snapshot lives in the run's artifacts folder, which must lie outside the worktree.
- A Temporal StartToClose timeout (`TimeoutFailure`) carries no `implement:` prefix and is not classed `size`; only provider-raised timeouts and no-progress kills are.
- Survey `old_paths` is clamped to 1..8 in `src/survey.ts`, so a survey item can only trip the area-count rule, not the 10-file cutoff; the survey S/M/L size is deliberately not mapped to the gate.
- `changedFiles` is not recorded in `metadata.size` or in e2e records.
- A `Stages:` directive line is ignored (and removed from the prompt) for projects without a tier and for the bug flow, without a warning.
- Manifest `onSizeFailure` is stored but only `manual` behaves.
- The merged task of `mergeSmall` keeps `Lane: light` even if the combined files exceed the small limit; a long merged prompt throws.

## Evidence
Dry run of the R3 shape (14 old paths over `src/a`, `src/b`, `src/c`, set after parsing because the schema clamps to 8) through `planFromBacklog` with `DEFAULT_SIZE_LIMITS.production`: no task is generated; `needsSplit` holds R3 with 14 files, 3 areas, reasons "14 files (large from 10)" and "3 areas (limit 2)", and a proposal of `src/a part 1 [6]`, `src/b part 1 [4]`, `src/c part 1 [4]`, each under 10 files. The dry run itself was a throwaway script. The same case is pinned by the Task 4 test "leaves a too-large item out of the tasks and proposes parts under the limit; prototype keeps it" in `test/plan-from-survey.test.ts`.
