# Unity / game support: analysis and plan (2026-10-24)

Status: analysis and plan only. Nothing is implemented. Decisions recorded with the user on 2026-10-24:
1. Integration: **Unity CLI first, editor MCP optional.**
2. Authoring: **code-first** (scenes, prefabs, UI generated by committed C# editor scripts run headlessly).
3. A mandatory **game-design stage (GDD + rules spec + test-case table) with human approval** before milestones/tasks are generated.
4. Test game assets: **procedural/vector art and free-licence assets**, no paid generation APIs.

Facts marked (verified) were read from the source page or this host on 2026-10-24; (reported) came from a search summary and must be re-checked before use.

Host facts (verified): Unity Editor 6000.3.11f1 with Android, WebGL and Windows modules; Unity CLI 1.0.0-beta.13 at `%LOCALAPPDATA%\Unity\bin\unity.exe`; JDK 21 and `gh` present; no `adb`; GPU Intel Iris Xe.

## 2. How the current orchestration is shaped

- `qualityCommands` accept only `node|npm|pnpm|yarn` (`ToolExecutableSchema`, `src/contracts.ts:18`); the server refuses code tasks without quality commands (`src/server.ts:89`).
- `prepareProjectDependencies` only knows npm (`src/activities.ts:97`). One template (Vite/React/TS, `src/bootstrap-templates.ts`); scaffold proves `npm test` + `npm run build`.
- Visual verification is Playwright against a dev-server URL (`src/visual.ts`, ADR 0007); bootstrap turns it off for non-web platforms (`bootstrap-options.ts:100`).
- Platform catalog has `mobile_android`, `mobile_ios`, `desktop` but no engine/game dimension; stack/charter/blueprint stages are generic.
- UI/UX guidance is a hard-coded catalog of 4 web/React skills (`src/uiux.ts`); the ADR 0010 design bar is web-flavoured.
- Providers run Claude/Codex/Gemini CLIs in the per-run worktree; `CLAUDE.md`/`AGENTS.md` and `docs/PROJECT_CONTRACT.md` are committed and auto-loaded (ADR 0009/0011), so skills can be delivered as repo files (`.claude/skills/`, `.agents/skills/`) with no provider code change.
- Rule: new optional gates live inside existing activities; command-sequence changes need `patched()` and a regenerated replay fixture. This plan is designed to avoid any workflow change.

Gaps for Unity: (1) non-Node executables, (2) non-Node dependency preparation, (3) a game-design stage, (4) engine-specific gates and visual evidence, (5) engine-specific skills, contract and design bar, (6) slow, licence-bound, single-instance Unity processes inside git worktrees.

## 3. Unity + AI-agent practices that drive the design

Sources: Unity CLI/skills docs above, GameCI activation docs, Unity manual command-line pages, git-for-Unity guides, headless-unity-mcp notes (reported items to verify at implementation).

1. **Text serialization and `.meta` files are mandatory**: Force Text, Visible Meta Files, commit `.meta` with every asset; `.gitignore` for `Library/ Temp/ Logs/ Obj/ UserSettings/ Builds/`; `.gitattributes` with `*.unity *.prefab *.asset merge=unityyamlmerge`, `*.asmdef -text diff`; LFS only for large binaries, never scenes/prefabs/metas.
2. **Agents must not hand-edit scene/prefab YAML**; GUID references break silently. Generate them through committed editor scripts and keep gameplay logic in plain C#. Hence "code-first": reproducible, diffable, reviewable.
3. **Testable architecture**: pure-C# logic assembly (`asmdef`, `noEngineReferences`), thin MonoBehaviour view layer, deterministic seeded RNG, EditMode tests for logic, PlayMode tests for scene wiring, a smoke test loading every scene. Asmdefs also cut compile time, which dominates agent-loop cost.
4. **Never trust Unity's exit code alone**: require the result XML and test count > 0; parse the build log verdict.
5. **Headless caveats**: `-batchmode` can force a null graphics device and `-nographics` disables rendering, so screenshot evidence needs a windowed (or minimised) run on a GPU machine (this host qualifies). Unity startup can hang: always timeout and kill the process tree.
6. **One Unity instance per project folder**; `unity test` refuses a project open in a running Editor. Each worktree is a separate project, and a cold `Library/` import takes minutes. Mitigate by seeding `Library` from a cached copy, limiting Unity concurrency to 1, and measuring (Phase 0).
7. **Licensing**: Personal licence on the already-licensed Windows host works for CLI runs (to be confirmed by a real run); Linux CI would need GameCI activation, out of scope.
8. **Mobile production baseline** (reported): IL2CPP + ARM64, Android App Bundle, target API per Play policy, safe areas, 44pt/48dp touch targets, Incremental GC, no per-frame allocations in hot paths, pooling, Input System, frame pacing, ASTC textures, profiling on a low-end device, signing from secrets never in argv logs.
9. **Games need more than passing tests**: design document, rules spec with edge cases, balance/feel targets, UX flows (first launch, pause, settings, game over, restart), juice (animation, haptics, sound), accessibility (colour-blind-safe tiles, scalable text, reduced motion), performance budget. Only the first and last are mechanically testable; the rest need evidence (screenshots, capture) and a rubric reviewer.
10. **2048 rules to pin before coding**: spawn 2 at 90% / 4 at 10%; a move that changes nothing spawns nothing and is invalid; each tile merges at most once per move, pairing from the wall side (`[2,2,2,2]` -> `[4,4]`, `[2,2,2]` -> `[4,2]` toward the wall); score = sum of merged values; explicit win/loss precedence and continue-after-win; game over only when the board is full and no adjacent equals; undo, best-score persistence, test seed. The "highest tile gets a special icon" requirement needs a recorded decision (icon on the current highest tile vs at milestone values); the design stage must settle it.

## 4. Target design

Principle: **a stack profile is data**, not code branches. Unity is the first non-Node profile; Node stays default and unchanged.

### 4.1 Stack profile (`src/stack-profiles.ts`, new)
Fields: `id` (`node-web`, `unity-mobile`), allowed executables, dependency-prep recipe, source extensions, ignore/attributes templates, quality presets per maturity, skill packs, design bar id, review rubric id, evidence strategy (playwright | unity-capture | none), concurrency class.
- `ToolExecutableSchema` becomes profile-derived. The Unity profile adds `unity` (resolved from doctor/env, args validated like `reproductionCommandProblem`: no arbitrary `-executeMethod`, no shell metacharacters).
- Manifest gets optional `stack: {profile, unity: {editorVersion, cliVersion, buildProfile}}`. Absent means today's behaviour, so existing manifests and the replay fixture are untouched.

### 4.2 Gates inside existing activities (no workflow change)
- `prepareProjectDependencies`: Unity recipe verifies `ProjectSettings/ProjectVersion.txt`, seeds/restores cached `Library`, runs an import/recompile with timeout; failure is non-retryable and clear.
- Quality commands: `unity test --mode EditMode` (fail), `unity test --mode PlayMode` (fail from MVP), `unity build --target Android --profile ci` (warn at MVP, fail at production), each followed by evidence assertions (XML exists, tests > 0, log verdict). A committed `scripts/check-unity-hygiene.mjs` (run via node, so no executable change) checks `.meta` presence, no `Library/` committed, asmdef rules, forbidden APIs, rule-id traceability.
- Evidence: `visual` strategy `unity-capture`: a committed PlayMode capture test writes PNGs of named states (menu, board, merge, game over, settings) to the artifacts dir; the review activity attaches them like Playwright shots. Severity `warn` by default, `required` at production.
- Optional perf gate: PlayMode frame-time/GC-per-frame measurements against manifest budgets; android-profiler skill only when `adb devices` is non-empty, otherwise skipped with a warning.

### 4.3 Bootstrap (project creation)
- **Catalog**: new "Game" option group in `bootstrap-options.ts` (`product_kind` app|game, `engine` auto|unity|godot|web, `genre`, `target_devices`, `orientation`, `input`, `session_length`, `art_pipeline` procedural|free|generated, `audio`, `performance_floor`, `monetization`, `localization`). The wizard renders from data. Platform rules: `engine=unity` selects the Unity capture strategy instead of disabling visual checks, picks Unity test/build presets, swaps the web design bar for the game bar.
- **New `design` stage** before `blueprint` via `structuredStage` (repair + deterministic fallback, added to `test/chaos.test.ts`). `GameDesign` schema: vision, core loop, numbered testable rules (`R-001`...), edge-case table, state machine, scoring/progression, balance targets, UX flow and screen list, feel/juice spec, audio list, accessibility, asset list, performance budget, risks, out-of-scope, plus a rule-to-test table. Committed as `docs/GAME_DESIGN.md` and `docs/RULES_SPEC.md`, shown in the Bootstrap tab and approved through the existing approval gate. Blueprint tasks cite rule ids and the gate checks every id has a test.
- **Game blueprint milestones**: M0 foundation (project, asmdef, hygiene, test and capture harness, architecture ADR), M1 core logic (pure C# rules + exhaustive tests), M2 playable slice (board view, input, animation), M3 UX shell (menus, settings, game over, persistence), M4 polish (juice, audio, accessibility, themes), M5 performance and release (profiling, Android AAB, signing, store assets). Sequential by default.
- **Template `unity-mobile-2d`**: layout, `.gitignore`, `.gitattributes`, pinned `Packages/manifest.json`, asmdefs, editor builder scripts, test asmdefs, capture test, hygiene script, Force Text/Visible Meta, Android IL2CPP/ARM64, build profile. It must be created by running Unity in batch once so GUIDs and `.meta` files are genuine. The scaffold proof becomes profile-driven (`unity test` EditMode + `unity build`).
- **Skill pack installed in the generated repo** (`.claude/skills/`, `.agents/skills/`): Unity official skills (pinned, licence recorded, installed at scaffold time rather than vendored here), our own `unity-game-director` router, `unity-testable-architecture`, `unity-ui-toolkit-mobile`, `game-design-rules-spec`, `unity-agent-hygiene` (never edit YAML/GUID/meta), `unity-perf-android`, and optional `android-profiler`. `CLAUDE.md`/`AGENTS.md` state the commands, rule-id convention and forbidden operations.

### 4.4 Skill packs generalised
Replace the hard-coded web catalog in `src/uiux.ts` with data-driven skill packs: `{id, source, pin, stages (design|plan|implement|review), match (profile|frameworks|intent), guidance, install}`. Existing web skills remain. Add `game-ui-mobile` (safe areas, 44pt targets, thumb reach, one-hand portrait play, haptics, tile contrast and colour-blind palettes, reduced motion, 60 fps animation budget), `game-feel`, `unity-architecture`, `unity-review-rubric`. ADR 0010's bar gets a `game` variant (visual identity doc, theme tokens, animation timing table, store-quality menus, first-launch/resume/loading/error/game-over states, evidence rather than claims).

### 4.5 Architecture and review
- ADR 0008 `architecture` task type is reused for a mandatory M0 architecture task (asmdef graph, data flow, save format, input abstraction, ADR in the repo).
- Unity review rubric (enforced by `applyReviewAssessment`): rule-id traceability, allocation hygiene, safe-area/input correctness, scene/prefab integrity (editor check script for missing references), screenshot scorecard (hierarchy, contrast, consistency, juice), performance budget.
- Optional assisted authoring plugin (off by default, later phase): IvanMurzak/Unity-MCP over stdio with token auth for the implement stage, against an Editor the operator opens on a copy of the worktree. Interactive only.

## 5b. Phase 0 spike log (2026-10-24, partial)

Verified on this host:
- Unity CLI 1.0.0-beta.13 offers `test`, `build` (`--target`, `--profile`, `--execute-method`, Android flags), `command`/`list`/`job` (live Editor), `ci`, `commands` (machine-readable manifest), `doctor`, `license`. `unity commands --json` is a candidate for a doctor check.
- The Android module bundles SDK (`platform-tools`, `build-tools`, `cmdline-tools`), NDK and OpenJDK under `Editor\Data\PlaybackEngines\AndroidPlayer`, so no separate Android Studio is needed, and an `adb` exists inside it.
- `Unity.exe` is a GUI-subsystem binary: from PowerShell it must be launched with `Start-Process -Wait -PassThru` or the exit code is lost. The orchestrator's runner must do the same (the CLI does this itself).
- **Blocker: no valid Unity licence.** `Unity.exe -batchmode -createProject` exits 198 with `No valid Unity Editor license found` / `'com.unity.editor.headless' was not found`; `unity doctor` shows `auth.loggedIn false`; no `Unity_lic.ulf` exists. Startup to licence failure took about 2.5 s. An agent cannot sign in on the user's behalf. Needs the operator to sign in to Unity Hub and activate a Personal licence (or provide a serial/service account) once. This must become a `doctor` check (`unity:licence`) and a bootstrap precondition, otherwise a Unity project fails at scaffold time.
- A hand-written spike project is prepared at `<scratchpad>\spike\hand` (version file, manifest with test-framework 1.6.0, a pure-C# merge function with asmdef, EditMode tests, a PlayMode capture test that writes a PNG and asserts the graphics device is not Null, and an Android AAB builder). Not yet run.

The licence blocker above was resolved later the same day (operator signed in; `unity doctor` shows `auth.loggedIn true`, Unity Personal). Results are in 5c.

## 5c. Phase 0 spike results (2026-10-24, licensed)

Throwaway project created with `Unity.exe -batchmode -createProject` (exit 0), hand-written logic/tests/builder copied in. All runs through Unity CLI 1.0.0-beta.13 on Unity 6000.3.11f1, Windows, Intel Iris Xe.

| Check | Result |
|---|---|
| `unity test --mode EditMode` | Passed 2/2, exit 0, NUnit XML written, 61 s including first package resolve and import. |
| `unity test --mode PlayMode` capture | After fixing the test: exit 0, **real Direct3D11 rendering in batchmode** (`SystemInfo.graphicsDeviceType = Direct3D11`), 540x960 PNG written, about 15-18 s warm. So the capture strategy works headlessly through `unity test` without a visible window. |
| `unity build --target Android --execute-method` (IL2CPP, ARM64, AAB) | **Succeeded from a short path (`C:\u\p`): `spike.aab` 13.9 MB, 264 s** (includes IL2CPP and Gradle). The same build from the 150-character scratchpad path failed after 374 s in Gradle with `ninja: error: manifest 'build.ninja' still dirty after 100 tries`. |
| Claude + official plugin | `claude -p --plugin-dir <clone of Unity-Technologies/unity-agent-plugin>` loaded the plugin headlessly, picked `unity:unity-cli` and returned the right `unity test`/`unity build` commands. Plugin v0.1.8-beta, commit `3831ddb`, 34 skills, `.claude-plugin` + `.codex-plugin`, no MCP server inside the Claude plugin (MCP comes from `unity mcp`), licence "Unity Companion License for Unity-dependent projects". |

Findings that change the design:
1. **Project path length matters.** Android IL2CPP builds fail on long paths (Gradle/ninja). Per-run worktrees live under deep folders, so Unity builds need a short worktree root (for example `C:\u\<run>`) or a short junction; add a `doctor` check and a path-length guard in the Unity runner.
2. **`unity test` is batchmode: no `WaitForEndOfFrame`.** A `[UnityTest]` that yields it fails with "not evoked in batchmode". The capture harness must render a camera to a `RenderTexture` and `ReadPixels`. Put this in the template's capture helper and in the agent guidance.
3. **The empty Unity template has no `com.unity.test-framework`.** Without it test asmdefs fail with `CS0246 NUnit`. The scaffold manifest must declare it (1.6.0 resolved on 6000.3).
4. **Test asmdefs must carry `defineConstraints: ["UNITY_INCLUDE_TESTS"]`.** Otherwise the Android player build compiles them and fails (`UnityTest` not found). Add to the hygiene script and the template.
5. **Do not use `optionalUnityReferences: ["TestAssemblies"]` together with explicit test-runner references** (duplicate reference error); agents tend to write both.
6. **The CLI surfaces compiler errors itself** (`CS0246 file(line,col): ...` lines), so the repair prompt can use its output directly; the full log is only kept when `--log-file` is passed (pass it, always, into the run artifacts). Exit codes confirmed: 0 passed, 8 tests failed, 6 no verdict or build failure.
7. First-run costs: package resolve plus import about 60 s, Android build about 4.5 min warm of Editor but cold for IL2CPP. Budget stage timeouts at 15 min for tests and 30 min for builds, and keep `Library` warm (seed from a cached copy).

Not measured: second concurrent Unity instance, `unity ci` scaffolding, `unity mcp`, a device/emulator run, a warm second Android build.

## 6. Risks and open items
- Unity CLI is beta (1.0.0-beta.13): pin, wrap behind our runner, keep a fallback to raw `Unity.exe -batchmode -runTests`.
- Cold import time and a single licensed host may make runs slow; Phase 0 decides `Library` seeding and concurrency.
- Unity Companion License terms for the official skills: confirm before vendoring; plan installs at scaffold time and records the pin.
- Android signing: release keystore only on the worker via secrets, never in prompts or argv logs; debug-signed AAB for the test game. `unity build --target Android` needs the SDK/NDK bundled with the module (present as the Android module; SDK completeness unverified).
- Model quality for scene/UI authoring is the weakest link; code-first builders plus the screenshot rubric mitigate; a generator/evaluator polish loop is an option if the first run scores low.
- iOS builds need macOS; out of scope.
